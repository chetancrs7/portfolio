## Overview

This is a **backend systems-design case study**, not a production system. It documents the architecture for a geospatial platform that would track hikers, evaluate spatial boundaries, and drive safety workflows — and it is explicit about what is actually built versus what is designed.

The honest split matters here, so it comes first: an **implemented NestJS/TypeScript API foundation** exists (modular app, a users module, a Jest test harness); the geospatial subsystems — PostGIS spatial storage, geofencing, time-series monitoring, workflow orchestration — are **designed and planned**, not yet implemented. > **Engineering question.** How do you design a backend that reliably manages
> continuously changing geographic state — while keeping spatial queries,
> monitoring, and safety workflows independently maintainable?

## Problem

A hiking-safety platform has to manage more than latitude and longitude. It manages **users and hikers**, **trails and routes**, **spatial boundaries**, a continuous stream of **location updates**, and **safety events** (boundary violations, SOS). The hard part is that these live at the intersection of three concerns that a naive CRUD backend collapses together:

- **Space** — is this hiker on the trail, inside a restricted zone, within range of another hiker? These are geometric questions, not equality checks on numeric columns.
- **Time** — a hiker's position is a stream. The _current_ position and the _history_ of positions have very different read/write patterns.
- **State & service boundaries** — "record a location" and "raise an SOS and notify someone" are different responsibilities with different reliability requirements, and shouldn't be one tangled handler.

The design goal is to keep those three concerns separable so each can be reasoned about, queried, and scaled on its own terms.

Component responsibilities, as designed:

- **Flutter client** _(planned)_ — user interaction, location transmission, displaying relevant state.
- **NestJS API** _(foundation implemented)_ — HTTP endpoints, validation, business logic, and the single write boundary. This is the part that exists.
- **PostgreSQL + PostGIS** _(planned)_ — relational domain entities and the **current** spatial state, with real geometry types and spatial indexes.
- **InfluxDB** _(planned)_ — high-frequency location **telemetry** as time-series.
- **Node-RED** _(planned)_ — workflow orchestration for events (geofence crossings, SOS) — deliberately _not_ a replacement for API business logic.
- **Grafana** _(planned)_ — internal operational dashboards over the telemetry store.

What _is_ implemented is the API foundation the location module would slot into — a NestJS controller/service with dependency injection. This is the actual current code:

```ts title="src/users/users.controller.ts" showLineNumbers
@Controller("users")
export class UsersController {
  constructor(private readonly usersService: UsersService) {}

  @Get()
  findAll() {
    return this.usersService.findAll(); // returns stubbed data today
  }

  @Get(":id")
  findOne(@Param("id") id: string) {
    return { id };
  }
}
```

It matters because it establishes the pattern every future module follows: a thin controller for the HTTP boundary, a service for logic, and DI wiring them — the seam where a real `LocationService` and repository would attach without rewriting the transport layer.

The proposed location DTO is where validation would live. Invalid geographic data must be rejected at the edge, because a single bad coordinate silently corrupts every downstream spatial operation:

```ts title="Proposed — CreateLocationDto (not yet implemented)"
export class CreateLocationDto {
  @IsUUID() hikerId: string;
  @IsLatitude() latitude: number;
  @IsLongitude() longitude: number;
  @IsISO8601() recordedAt: string;
}
```

## Spatial Data

The core decision is to treat coordinates as **geometry**, not two float columns. PostGIS is the reason PostgreSQL is the chosen relational store: it adds real spatial types, spatial indexes, and geometric predicates, so "is this point inside this polygon?" and "who is within 500 m?" become database operations instead of application-side loops.

At the API boundary the design uses **GeoJSON**, because it maps cleanly onto the domain and is a well-understood interchange format:

- **Point** → a hiker location
- **LineString** → a trail route
- **Polygon** → a geofence / zone boundary

```json title="GeoJSON — note the coordinate order is [longitude, latitude]"
{ "type": "Point", "coordinates": [77.5946, 12.9716] }
```

That ordering is a classic source of bugs: GeoJSON and PostGIS `ST_MakePoint` both take **longitude first**, while most human-facing UIs say "lat, long". The DTO validation above is what pins the order down before it reaches the database.

A representative proximity query — **conceptual**, illustrating the intended pattern rather than shipped code:

```sql title="Conceptual — hikers within 500 m of a point"
SELECT hiker_id
FROM location_current
WHERE ST_DWithin(
  geom::geography,
  ST_MakePoint(:lng, :lat)::geography,
  500  -- metres, because ::geography uses metres
);
```

**Spatial indexing (planned).** Without an index, `ST_DWithin` degrades to a scan over every row. The design specifies a **GiST index** on the geometry column so the planner can prune to a small candidate set via bounding boxes before running exact geometry math — the difference between a query that scales and one that does not.

## Geofencing

A geofence is a polygon boundary; the system needs to know whether a hiker is inside it and, more usefully, when they **cross** it. The design evaluates this with **Turf.js** (`booleanPointInPolygon`) for lightweight in-process checks, comparing the previous and current boundary state to derive enter/exit transitions.

```ts title="Conceptual — boundary check with Turf.js"
import booleanPointInPolygon from "@turf/boolean-point-in-polygon";
const isInside = booleanPointInPolygon(hikerPoint, trailBoundary);
// enter/exit is derived by comparing isInside to the previous state
```

## Data Model

The entities are intentionally few, and the model separates **current state** (relational + spatial, in PostGIS) from **historical telemetry** (time-series, in InfluxDB). That separation is the most important data decision in the design.

**Why PostgreSQL + PostGIS for current state:** the domain is relational (users own hikers; trails define zones), needs transactional consistency for safety events, and needs spatial predicates. PostGIS gives all three in one store. This is a fit for _this_ workload, not a claim that PostgreSQL is universally best.

**Why InfluxDB for history:** position updates are a high-frequency, append-only, time-ordered stream that is almost always queried by time window. That is exactly a time-series workload. PostgreSQL _can_ store it, but a dedicated time-series store keeps high-rate telemetry writes off the transactional database and makes retention and time-bucketed queries first-class. The tradeoff is a second datastore to operate — accepted deliberately, and discussed below.

## Infrastructure & Observability

The intended runtime is a **Docker Compose** stack so the whole system is reproducible locally with one command and each service stays isolated. None of this is stood up yet — it is the target deployment.

The key architectural discipline is keeping these boundaries clean: **NestJS** owns business logic and the write path; **Node-RED** orchestrates event-driven side-effects (a geofence crossing → a notification) without absorbing core logic; **PostGIS/InfluxDB** own persistence; **Grafana** owns visualization. Observability is intentionally split — InfluxDB + Grafana for telemetry — and its current gaps (no metrics/tracing/health-check wiring yet) are stated plainly rather than papered over.

## Scalability & Tradeoffs

No load testing has been done, so nothing here is a measured number — this is architecture reasoning about where the design would strain first.

**Architecture thought-experiment.** Suppose 1,000 active hikers each send one update every 5 seconds → **~200 updates/second**. That is modest for a single API instance, but it stresses specific places: transactional spatial writes to PostGIS, telemetry writes to InfluxDB, and geofence evaluation on every update. The point is not the number — it is identifying _which_ components feel write pressure first.

**Potential bottlenecks** (not observed — reasoned): high-frequency location ingestion, per-update spatial queries, geofence evaluation, and notification fan-out. Three of these are write-amplifying, which is why the design separates telemetry from transactional state up front.

**Backpressure.** Today there is **no queue** — the API would write synchronously. The scaling answer is to put an ingestion queue between the device and persistence so bursts are absorbed by workers rather than dropped:

An **event-driven evolution** follows naturally: emit `LocationUpdated`, `GeofenceEntered`, `GeofenceExited`, `SOSTriggered`, and let notification, analytics, and audit consumers subscribe independently. This is **future architecture**, not current behaviour.

**Tradeoffs**, grounded in the actual design decisions:

| Decision                      | Benefit                                                  | Cost                                                     |
| ----------------------------- | -------------------------------------------------------- | -------------------------------------------------------- |
| PostgreSQL + PostGIS          | Relational integrity + real spatial queries in one store | Spatial workloads and indexes add operational complexity |
| Separate InfluxDB for history | High-rate telemetry writes stay off the transactional DB | A second datastore to run and reason about               |
| Node-RED for orchestration    | Visual, decoupled event workflows                        | An extra runtime; must resist leaking core logic into it |
| Docker Compose                | Reproducible, isolated local environment                 | Local-only; not a production deployment                  |

## What I Learned

- Geospatial data is not "two float columns" — treating coordinates as geometry (PostGIS) turns spatial questions into database operations and makes indexing possible.
- Current state and historical telemetry are **different workloads**; matching each to the right store (PostGIS vs InfluxDB) is a clearer design than forcing one database to do both.
- Service boundaries should follow responsibility: business logic, workflow orchestration, persistence, and visualization each belong in their own layer, and coupling them is the easy mistake.
- Scaling location ingestion is fundamentally about **write volume and backpressure** — the queue-and-workers pattern is the honest answer, and it belongs in "future work" until the numbers demand it.
- Safety features need explicit failure handling designed in, not bolted on — a notification path that can fail must never block ingestion.
