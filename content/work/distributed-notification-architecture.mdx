## Problem

Notification systems fail in ways that are easy to hide during happy-path demos: duplicate sends, delayed workers, provider outages, queue overload, and unclear delivery state. This design study models those failures directly.

<Callout type="warning">
  This is a design study. Scale numbers are assumptions, design targets, or
  estimates, not measured production results.
</Callout>

## Scale Assumptions

ASSUMPTION: traffic arrives in bursts around product events.

DESIGN TARGET: delivery fan-out can be higher than request volume.

ESTIMATE: queue depth and retry windows are tuned from stated assumptions, not measured production traffic.

## Capacity Estimates

The first capacity model should size queues and workers around peak fan-out, provider rate limits, and retry amplification. Concrete numerical estimates should be added only when the assumptions are finalized.

## Component Deep Dives

The API owns validation and idempotent intent creation. Workers own provider translation, retry behavior, and attempt recording. The queue boundary prevents provider latency from blocking product services.

## Failure Scenarios

<FailureMode
  title="Worker Crash"
  failure="A worker terminates after sending to the provider but before acknowledging queue work."
  behavior="The message can be redelivered and processed again."
  protection="Attempt records and idempotency keys make duplicate side effects visible and bounded."
/>

<FailureMode
  title="Provider Outage"
  failure="A downstream provider rejects requests or times out for one channel."
  behavior="That channel retries with backoff while other channels continue processing."
  protection="Channel isolation, retry budgets, and dead-letter queues prevent infinite retry loops."
/>

## Scaling Strategy

Scale horizontally at the worker layer first, then split queues by channel or priority when one delivery mode starts starving another. Provider rate limits remain the real ceiling.

## Observability

- Queue depth and oldest-message age.
- Provider success, timeout, and rejection rates.
- Dead-letter count by template, channel, and provider.

## Security

Notification payloads should minimize sensitive fields, use scoped service credentials, and avoid logging full message bodies unless an explicit debugging path is enabled.
