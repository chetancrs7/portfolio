## Overview

This case study treats sentiment inference as a backend-ready AI system, not just a model score. The system combines a semantic expert with structural linguistic features, then records enough model behavior to make evaluation and future serving decisions inspectable.

The project is useful because it separates three concerns: model quality, model confidence, and the service boundary that would eventually expose predictions to application code.

</Callout>

## Problem

Traditional sentiment systems tend to lean on either semantic representation or engineered structural signals. Transformer-style semantic features capture context, but can be overconfident on short or sarcastic text. Structural features can preserve useful surface patterns, but are weaker when the meaning depends on context.

The engineering problem is to combine both views while keeping the result interpretable enough to operate behind a backend API.

## Backend Design

The backend interface should make inference an explicit capability with input limits, model versioning, request identifiers, and structured outputs. Application code should not depend on the internals of the model architecture.

A synchronous endpoint is acceptable for short interactive requests, but larger workloads should move to queued batch inference. That keeps the user-facing boundary stable even if feature extraction or model runtime changes.

## AI / ML Architecture

The model combines semantic representations with structural features. Mean gate alpha is tracked because it describes model behavior, not just score. A high gate alpha means the semantic expert carries most of the final signal.

> The gate heavily favors the semantic KAN expert. Fusion improves only modestly over KAN despite a higher oracle ceiling, which suggests complementarity exists but is not fully exploited.

## Security

The serving boundary should validate input size, reject malformed payloads, avoid logging raw sensitive text by default, and expose model metadata without leaking training artifacts.

## Deployment

The deployment design should separate the application API from the model runtime so CPU-bound or GPU-bound inference can scale independently when real traffic data justifies it.

## Observability

- Track request volume, latency buckets, timeout rate, and model version.
- Record confidence and calibration-oriented aggregate metrics without storing unnecessary raw text.
- Separate application failures from model-quality drift.
